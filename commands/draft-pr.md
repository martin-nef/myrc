description: Open a concise draft pull request on GitHub for the current branch
---

Open a **draft** pull request on GitHub for the current branch using the `gh` CLI.

# Preconditions

1. **Must be inside a git repo.** Run `git rev-parse --is-inside-work-tree`. If not, stop and ask the user to point you to a repo directory — do not proceed.
2. **Must be on a non-default branch.** Determine the default branch (try in order: `gh repo view --json defaultBranchRef -q .defaultBranchRef.name`, fall back to `git symbolic-ref refs/remotes/origin/HEAD --short | sed 's@^origin/@@'`, then `main`/`master`). If the current branch equals the default branch, ask the user which branch name to create and switch to before proceeding. Do not silently invent a branch name.

# Gather context

Run these in parallel to understand what is being shipped:

- `git status` — uncommitted changes
- `git log <default-branch>..HEAD --oneline` — commits on this branch
- `git diff <default-branch>...HEAD` — full diff vs default branch
- **Locate the PR template** by exploring the repo (common conventions include `.github/`, `docs/`, and the repo root; templates are usually markdown). If you find one, read it and use it as the body skeleton. If you find none, proceed without one — write a short, well-structured body from scratch (purpose, brief context, overview of changes).

If there are uncommitted changes, proceed with the PR for what's already committed and ask the user afterwards what to do about them — do not auto-commit and do not block on asking up front.

Push the branch with `git push -u origin HEAD` if it has no upstream.

# PR title

The title **should** start with a prefix in CAPS followed by a colon `:` and a concise summary, e.g.:

```
SEMO-123: Add retry logic for failed payouts
```

or, when there's no ticket but a team owns the change:

```
PAYMENTS: Add retry logic for failed payouts
```

Resolve the prefix in this order — **stop at the first match**:

1. **Ticket slug from the current branch name.** Look for a `[A-Z]+-\d+` pattern (case-insensitive) anywhere in the branch name and uppercase it (e.g. `semo-123-foo` → `SEMO-123`, `feature/abc-42_thing` → `ABC-42`).
2. **Ticket slug from `$ARGUMENTS`** if the user passed one (e.g. `/draft-pr SEMO-123`).
3. **Team slug from `$ARGUMENTS`** if the user passed a non-ticket uppercase token (e.g. `/draft-pr PAYMENTS`). Uppercase it.

If none of the above yields a prefix (no ticket in the branch name AND no slug in `$ARGUMENTS`), **omit the prefix entirely** — do not ask, do not invent one. The title is then just the concise summary.

Always uppercase whichever prefix you use. Keep the full title short (under ~70 chars).

# PR body

**Always generate the body yourself from the PR template** and pass it via `--body`. Never rely on `gh`'s built-in template auto-fill (do not pass `--body-file` pointing at the template, do not omit `--body`).

Guidelines:
- Read the template file, use its section headings as the skeleton.
- Keep it **concise** — reviewers should be able to skim it in 30 seconds. Lead with the *why* and a brief context, then a short bullet overview of the changes. Skip sections that don't apply rather than padding them.
- Strip HTML comments (`<!-- ... -->`) and template placeholder text from the final body.
- Do not paste the diff. Do not enumerate every file. Bullet the meaningful changes only.
- At the very bottom of the body, append a short disclaimer on its own line:

  ```
  _PR description generated by Claude._
  ```

# Create the PR

Use a HEREDOC so the body formats correctly:

```
gh pr create --draft --title "<PREFIX: short summary>" --body "$(cat <<'EOF'
<generated body>
EOF
)"
```

After it succeeds, output the PR URL to the user.

If `gh pr create` fails because a PR for this branch already exists, do not retry creation. Instead, **overwrite the existing PR's title and body** with the values you just generated using `gh pr edit --title "..." --body "..."` (same HEREDOC pattern for the body). Don't change its draft/ready state. Then output the existing PR's URL.

# Important

- **Draft only.** Never pass `--ready` or call `gh pr ready` — the user marks it ready after CI passes.
- Prefix rules: ticket slug from branch > slug from `$ARGUMENTS` > team slug from `$ARGUMENTS` > no prefix. Never invent a slug.
- Do not push to or open PRs against branches other than the current one without confirmation.
